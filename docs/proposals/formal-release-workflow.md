# 提案：正式版推进工作法（调研 → 复测 → 文档集驱动）

## 一句话提案

总目标只有一个：把《心跳在左，拳头在右》做成一个合格的正式版游戏。推进方式要有目标、有条理：助手先补知识、再亲自复测总结问题，然后用一套固定文档驱动后续所有优化，不再零散地想到哪改到哪。

## 背景与来源（均为 2026-11-10 用户原话大意）

- 「之前继续做吧，不过也许你并不知道后面要做什么，因为很多优化的东西我没办法一个一个告诉你，也许你可以先去 GitHub 找找游戏开发相关的项目、知识、skills，然后再继续优化。总之我需要你完成的目标就是一个合格的正式版游戏。」
- 「你找到了开发相关的知识之后，重新自己总结测试游戏现在有的问题，然后整理一套文档，分别是：需要做的东西、具体的实现方法、实现之后的测试，里面内容记录改动历史。」
- 「这样能够有目标有条理去做。」
- 同日补充：每个提案单独写一个小文档、同话题持续更新（见本目录 `README.md`）。

## 方案要点

流程固定为四步，后续每个优化批次都走同一条路：

1. **调研**：去 GitHub 及公开网络找同类项目、发布清单、game feel、平衡测试、2D 骨骼模块化等知识，落成带真实链接的调研报告，提炼成可执行条目。
2. **复测**：助手亲自实跑当前版本（冒烟、生涯模拟游玩、战斗实验室、关键流程），问题清单以实测证据为准，不沿用旧结论。
3. **文档集**：把结论整理成四份互相链接的文档——
   - 需要做的东西（问题与目标，按优先级）
   - 具体实现方法（每项的路线与步骤）
   - 实现之后的测试（每项的验收方法与通过标准）
   - 改动历史（每项改动何时做、做了什么、测试结果）
4. **按文档集执行**：已批准事项（如纸偶模块化扩围）并入文档集排期；需用户拍板的事攒进 `../OPEN_ISSUES.md` 一次问，不阻塞其余工作。

验收口径沿用既定方针：好不好玩以助手模拟游玩的实际体验为准，不以冒烟断言数量代替（2026-11-03 用户定的游戏性优先）。
